# 把 Twenty Twenty-Three 部署到 GitHub Pages —— 分析与方案

> 结论先行：**WordPress 主题不能直接跑在 GitHub Pages 上**（Pages 只提供静态文件）。
> 但 TT3 是特例中的好消息：它是一个"纯声明式"主题，几乎所有视觉输出都可以在构建期一次性渲染成静态 HTML。
> 本仓库实现并验证了**路线 A（真 WordPress 渲染 → 静态导出）**，35 个页面、3.3 MB 产物，与主题演示站像素级一致。

---

## 1. 主题分析：Twenty Twenty-Three 到底是什么

来源：<https://wordpress.org/themes/twentytwentythree/>（WordPress 6.1 默认主题，GPL-2.0-or-later，当前 1.7 版）

下载官方 zip（2.1 MB）解包后共 51 个文件，结构非常"薄"：

```
twentytwentythree/
├── style.css        # 只有主题头注释（1.1 KB），没有任何 CSS 规则
├── theme.json       # 15 KB —— 整个主题的设计系统全在这里（v2 schema）
├── templates/       # 9 个 .html 区块模板（index/single/page/home/archive/search/404/blank/blog-alternative）
├── parts/           # header / footer / comments / post-meta 四个模板部件
├── patterns/        # 8 个 PHP 区块图案（只是带翻译函数的静态标记）
├── styles/          # 10 个风格变体 JSON（aubergine/canary/electric/grapes/marigold/pilgrimage/pitch/sherbet/whisper/block-out）
└── assets/fonts/    # DM Sans / IBM Plex Mono / Inter / Source Serif 4（默认风格根本不用，用的是系统字体栈）
```

三个关键事实，直接决定了部署方案：

1. **没有 `functions.php`，没有 `index.php`，没有一行手写 CSS**。TT3 的"PHP 依赖"几乎为零——模板是 HTML 注释包裹的区块标记（`<!-- wp:group /-->`），样式全部由 WordPress 在运行时从 `theme.json` 生成 CSS 自定义属性（`--wp--preset--color--base` 等 5 个色板、6 档 fluid spacing、5 档 fluid font-size、5 个字体族）+ 核心区块库 CSS（`wp-includes/css/dist/block-library/*`，约 114 KB）。
2. **"动态"的部分其实很有限**：查询循环（首页文章网格 + 分页）、站点标题、导航（无 ref 时回退为页面列表）、文章元信息、评论、搜索表单。这些是服务器端渲染的区块，不是客户端 JS。
3. **运行时刚需只有三样**：PHP + MySQL（内容查询）、`wp_head()`（生成全部内联 CSS/区块 CSS 链接）、REST/XMLRPC 等管理接口（静态站根本不需要）。

### 1.1 GitHub Pages 能提供什么、缺什么

| WordPress 需要 | GitHub Pages |
| --- | --- |
| PHP 8.x 解释器 | ❌ 只有静态文件服务 |
| MySQL / SQLite | ❌ |
| `wp_head` 每次请求生成 CSS | ❌ 必须构建期一次性产出 |
| 评论提交（`wp-comments-post.php`） | ❌ 无后端表单处理 |
| `?s=` 服务端搜索 | ❌ 只能换成客户端索引 |
| 固定链接路由（`/%postname%/`） | ✅ 目录 + `index.html` 天然等价 |
| 主题的全部视觉（区块 CSS + theme.json 令牌） | ✅ 可以原样复制 |

所以问题不是"能不能部署"，而是**在哪里完成渲染**。三条路线：

## 2. 三条路线对比

### 路线 A：真 WordPress 渲染 → 静态导出（本仓库采用 ✅）

在一个**无头的真 WordPress**（[WordPress Playground](https://developer.wordpress.org/playground/)，PHP 编译成 WASM，Node 一条命令拉起，不需要装 PHP/MySQL/Docker）里激活 TT3、灌入内容，然后抓取每个页面的**成品 HTML**（含 WP 从 `theme.json` 生成的全部内联 CSS 和核心区块 CSS），落盘为静态文件。

- 保真度：**100%**。拿到的就是 WordPress 自己渲染的 DOM，连 `wp-container-core-group-is-layout-2` 这类按布局哈希生成的容器规则都原样保留。
- 写作体验：Markdown（`content/posts/*.md`）→ 构建时编译成合法 Gutenberg 区块标记。想回到真 WP 时，这些内容可以原样导回。
- 成本：构建约 40 秒；产物 3.3 MB / 35 页。
- 适合：想要"主题长什么样就长什么样"的人。

### 路线 B：手工移植设计系统（Astro / Eleventy / Hugo）

不跑 WordPress，把 `theme.json` 的令牌翻译成 CSS 变量，把 9 个模板和 8 个图案手工重写成 SSG 组件，再自己实现查询循环/分页/归档。

- 保真度：90–95%。`theme.json` → CSS 的换算（fluid typography 的 clamp 公式、`useRootPaddingAwareAlignments` 的负边距对齐）必须自己复刻，差之毫厘视觉就歪。
- 优点：长期零 WP 依赖、构建秒级、组件可自由改。
- 成本：**2–4 周工作量**，且 WP 每次升级区块 CSS 都可能漂移。
- 适合：本来就打算深度魔改设计的人。

### 路线 C：装个真的 WordPress（放弃 Pages）

如果需要评论、后台、插件生态——Pages 从一开始就是错的选择。用任意 PHP 主机 / [wordpress.com](https://wordpress.com) 更省事。这是诚实的备选，不是失败。

> 附：也有 Simply-Static / Staatic / WP2Static 这类 WP 插件做导出，但它们需要**已经在跑的 WordPress**（通常还联着生产库），本仓库用 Playground 把这一步变成了"npm run build"。

## 3. 路线 A 的实现（本仓库）

```
content/                 # 你写的东西：Markdown + front matter
  site.json              # 站点名/描述/每页篇数/风格变体/域名
  posts/*.md             # 文章（title/date/category/tags/excerpt/cover）
  pages/*.md             # 页面（自动组成导航，TT3 导航块回退为页面列表）
theme/twentytwentythree/ # 官方主题原样保留（只挂载、不修改）
scripts/
  build.mjs              # 编排：编译内容 → 拉起 Playground → 抓取 → dist/
  export.mjs             # 抓取器/改写器（URL 重写、CSS 合并、SEO 注入）
  playground/seed.php    # 在 WP 里建文章/分类/标签/特色图/评论/风格变体
  preview.mjs            # 本地按部署 basePath 预览 dist/
dist/                    # 产物（也可由 CI 生成）
```

### 3.1 构建流水线

1. **编译内容**：Markdown → Gutenberg 区块（`lib/markdown.mjs`，零依赖）；按文章序号生成抽象渐变封面 PNG（`lib/png.mjs`，纯 Node 写 PNG，1200×800）。
2. **拉起 WordPress**：`@wp-playground/cli` + 蓝图（`activateTheme` + `runPHP` 灌种子数据）。主题目录用 `--mount-dir` 只读挂载。
   - 踩坑①：`runPHP` 步骤跑在**裸 PHP**里，`wp_insert_post` 不存在——必须先 `require '/wordpress/wp-load.php'`。
   - 踩坑②：CLI 在蓝图步骤**还没跑完时就开始对外服务**，抓取要等 `.seeded` 标记文件出现（挂在宿主目录上直接可见）。
   - 踩坑③：固定链接必须 `$wp_rewrite->set_permalink_structure()` 再 `flush_rules(true)`；只 `update_option` 的话内存里的规则还是旧的，文章页会被重定向回首页。
3. **抓取**：从 `/` 开始 BFS 同源链接，跳过 `wp-admin|wp-json|xmlrpc|feed`；另请求一个不存在的路径拿 404 模板。
4. **静态化改写**（`export.mjs`）：
   - 收集所有页面的内联 `<style>` + 外链区块 CSS，按规则去重合并成单个 `assets/css/site.css`（68 KB，gzip 后约 12 KB）；
   - 下载所有图片（含 srcset 的 300/768/1024 多档）与字体到原路径；
   - URL 重写：`http://127.0.0.1:9400/…` → `${BASE_PATH}…`（项目站点子路径可配）；
   - 剥离：全部 `<script>`（WP 交互运行时）、`<link>`（REST/RSD/短链接/dns-prefetch）、emoji 脚本、generator meta；
   - 评论表单换成"评论已关闭"提示（保留评论列表本身）；页脚 `Proudly powered by WordPress` 改为致谢主题；
   - 搜索表单 `action` 指向 `/search/`：一个用 TT3 自己的 `wp-block-post-template` 标记渲染结果的纯前端搜索页（索引构建时生成，1.9 KB）；
   - 注入：`<html lang>`、meta description、canonical、Open Graph/Twitter 卡、SVG favicon。
5. **附属产物**：`sitemap.xml`、`robots.txt`、`.nojekyll`（防止 Pages 用 Jekyll 处理 `wp-*` 目录）、可选 `CNAME`。
6. **移动端菜单**：WP 的汉堡菜单靠 `@wordpress/interactivity` 运行时，静态版用 26 行 vanilla JS 直接切换 `is-menu-open`/`has-modal-open` 类（CSS 是核心自带的，行为完全一致）。

### 3.2 十个风格变体

`theme/twentytwentythree/styles/*.json` 都是 `theme.json` 的局部覆盖。构建时在 `content/site.json` 里设 `"styleVariation": "marigold"`，`seed.php` 会创建 `wp_global_styles` 文章（等价于在站点编辑器里点了一下变体），重新 build 即可整站换肤——字体文件也会被一并抓取。

### 3.3 已知限制（静态化的必然代价）

| 功能 | 处理方式 |
| --- | --- |
| 评论发表 | 关闭；评论区显示"评论已关闭"。需要互动可接 Giscus/Utterances（GitHub 仓库即后端） |
| 服务端搜索 | 换成构建期生成的客户端索引（中文按子串匹配，够用；要分词可换 Pagefind） |
| RSS/feed | 未导出（Pages 对 `/feed/` 无目录索引文件映射） |
| WP 后台/编辑器 | 不存在——这正是静态化的意义 |

## 4. 部署步骤（GitHub Pages）

本仓库实际部署在 `Syerain/Syerain.github.io`（用户站点，根路径发布），采用**双分支**布局：

- `source` 分支 = 全部源码（日常只推这里）；
- `main` 分支 = 纯构建产物，由 `.github/workflows/deploy.yml` 构建后强推覆盖。

工作流同时走了两条发布通道，两种 Pages 配置都能吃到：**从分支部署（main 根目录）** 为主通道，**Pages API（GitHub Actions 模式）** 为备用通道（分支模式下备用通道会失败但不影响主通道）。仓库是 `<用户名>.github.io` 时自动按根路径构建，普通仓库则自动带 `/仓库名/` 子路径前缀——无需改配置。

通用流程（换任何仓库都适用）：

1. 推 `source` 分支（或把源码放 `main` 并把工作流触发分支改成 `main`）。
2. Settings → Pages → Source 选「Deploy from a branch: `main` / (root)」。
3. 推送后约 1 分钟生效；自定义域名填 `content/site.json` 的 `customDomain`（构建会生成 `CNAME`）。

本地验证：

```bash
npm install
npm run build          # → dist/（约 40 s）
npm run preview        # http://127.0.0.1:4321/tt3-pages/（按部署子路径服务）
node scripts/shots.mjs # Playwright 截图回归（可选）
```

## 5. 合规性

- TT3 与 WordPress 核心区块 CSS 均为 **GPL-2.0-or-later**，静态导出的衍生作品继续以 GPL 分发即可（保留 `theme/readme.txt` 与版权头）。
- 主题捆绑字体：DM Sans / IBM Plex Mono / Inter 为 OFL，Source Serif 4 为 OFL——OFL 允许再分发，保留各目录下的 `LICENSE/OFL.txt`（导出默认风格用不到字体，需要时按 3.2 换变体即可）。
